# Data Conventions

> **Status: draft, 10 November 2026; village IDs added 15 November 2026.** Rules marked **(confirm)** are inferred from what the data does today and need the maintainer's confirmation before they are enforced.

How faalupega data is recorded, who may change it, and how it relates to the other data the platform uses. Read this before adding or editing a village.

## 1. Sources of truth

The platform has four kinds of data. Each has one owner. They are never merged into one record; they are linked by village ID.

| Data | Owner | Where it lives | Who can change it |
| --- | --- | --- | --- |
| Faalupega text, per book edition | Maintainer, verified against the book | This repo, one file per village per edition | Maintainer only, by reviewed PR |
| Census boundaries | Third party (2011 census) | `faalupega-map-ui`, generated by a script | Nobody by hand; re-run the script |
| Links from village ID to census areas | Maintainer | One file in the shared core package (planned) | Maintainer, by PR |
| User content (accounts, user versions) | Each user | A database (planned, not built) | Each user, their own |

## 2. Book editions

- An edition is a transcription of one printed book. `version` holds its identifier (`"1930"`), and each edition has its own directory: `src/data/villages/<edition>/`.
- An edition record changes for one reason only: to match the book more closely. Every change goes through a PR that the maintainer checks line by line against the source.
- **Verified means merged to `main`.** Data in an open PR is unverified and must not be shown to users.
- No user of the platform can ever change an edition. See section 6.
- The source citation and copyright note live in `DATA_SOURCES.md` (added by PR #24). Page references per village are not recorded (decided 10 November 2026).

## 3. Village identity

Every village has one global ID in its `id` field, used by the CLI, the MCP server and the web app. The 56 villages on `main` were assigned theirs on 15 November 2026.

- Format: `<district>/<village>`, for example `vaisigano/fagasa`.
- Lowercase ASCII with hyphens. No macrons, no glottal stops.
- The district part is one of the 11 official districts, listed in `src/data/districts.ts`: `tuamasaga`, `aana`, `aiga-i-le-tai`, `atua`, `vaa-o-fonoti`, `faasaleleaga`, `gagaemauga`, `gagaifomauga`, `vaisigano`, `satupaitea`, `palauli`.
- Always qualified by district, even when the village name is unique today. Two villages named Papa are `vaisigano/papa` and `palauli/papa`.
- The maintainer decides the district. An ID needs only the right district; a village with no boundary in the census still gets its ID.
- An ID never changes once assigned. If one is found to be wrong after release, the correct ID is added and the old one redirects to it (redirects are planned, not built).
- The ID identifies the village, not the record. A record is the ID plus a version, so every edition and every user version of a village shares the same ID.
- A record the book prints for several villages together has one ID, with the names joined by hyphens: `palauli/gautavai-sili-vaiala`.
- `name` and `district` stay as display fields. `district` holds the district as the edition names it (for example `O le Itu-o-Tane`), which can differ from the district in the ID. Tafua is the reverse case: the census places it in Palauli, and the maintainer keeps it in Faʻasaleleaga as the book does.
- A new village PR adds the `id` for each village it adds. The data tests check the format, the district and that no ID is used twice in an edition.

## 4. Text

- Macrons are kept: ā, ē, ī, ō, ū.
- The glottal stop is `ʻ` (U+02BB). Never a straight apostrophe or a curly quote.
- An em dash printed inside a tulou line is kept inside the string as U+2014. **(confirm)**
- Spelling follows the line as verified against the book. The same title can be spelled differently in two sections of one village (Tafua has both `Mataʻutia` and `Matautia`); do not harmonise them. **(confirm)**
- Search ignores case, macrons and glottal stops, so none of this affects finding a record.

## 5. Entries and remarks

A `TitleEntry` is `{ title, details[] }` and follows the book's `Title — Detail` line. Entries with no detail confirmed 13 November 2026; the data tests allow them in every section.

| The book prints | Record it as |
| --- | --- |
| `Tofa — Lagi` | `{ title: "Tofa", details: ["Lagi"] }` |
| A name on its own, such as a malae with no detail | `{ title: "Malaeola", details: [] }` |
| A remark attached to a title: `Fanene — E tapa fua` | `{ title: "Fanene", details: ["E tapa fua"] }` |
| A remark on its own line: `E tapa fua isi alii` | `{ title: "E tapa fua isi alii", details: [] }` |

- An entry with no detail uses an empty array, never `[""]`.
- A section the village does not have is an empty array (required sections) or left out (optional sections).

## 6. User versions (planned, not built)

How the platform will handle disagreement with a book:

- A user who believes an edition is wrong copies that village's edition record into their own version.
- The user edits their version freely and may publish it for other users to see.
- A user version keeps the village's ID, uses the same record shape as an edition, and records its owner and which edition it was copied from.
- User versions live in the database. They never flow back into this repo and never change an edition.

Open questions are tracked in the plan doc: whether search includes published user versions by default, whether publishing needs review, and what happens to copies when an edition record is corrected.

## 7. Census and map data

- The map's boundaries live in `faalupega-map-ui` and come from the 2011 Population and Housing Census enumeration areas (Pacific Data Hub, SPC/SDD, CC-BY 4.0).
- `scripts/dissolve-samoa-villages.py` merges 876 enumeration areas into 306 villages by trimming suffixes from area names. The village shapes and names are that script's output, not an official village list. Some names are cut to 10 characters.
- Never edit the generated files by hand. Change the script and re-run it.
- A map village's `eaid` is the lowest enumeration area code in the village. Its `id` is a row number and is not stable; do not link to it.
- Faalupega villages and census villages do not match one to one. Never match them by name: Matautu, Safune and Lealatele each exist on both islands.

## 8. Storage format

- Today: one TypeScript file per village, plus two hand-maintained index files.
- Planned: one JSON file per village per edition, validated by a schema, with the index built automatically.
- The conversion waits until village PRs #18 to #23 are merged, so the review in progress is not disturbed. It will be checked by a test that the converted data equals the TypeScript data exactly.
- The faalupega text stays in git. A database is only for user content, and is loaded from these files one way.

## 9. Known issues (15 November 2026)

- Fixed in PR #18 (13 November 2026): the data tests now allow `details: []`; `iva.ts` no longer has `details: [""]`; straight apostrophes in village files are now `ʻ` (U+02BB).
- `asau.ts` holds two numbered names in one title (`1. Matiʻa 2. Matiʻatuʻau`). How to record a numbered pair needs a decision.
- Village PRs #20 to #23 conflict with `main`, because each edits the same two index files. Each also needs an `id` added per village before it merges.
- Vitest also runs the tests of a stale worktree under `.claude/worktrees/`, which adds 18 unrelated failures to the output.
